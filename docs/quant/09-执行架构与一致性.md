# 执行架构与一致性（回测 / 模拟盘 / 实盘）

本文说明 FastTrade 量化执行层的结构、买入点的完整判定链路、三种运行模式的差异边界，以及
"哪些偏差是设计取舍、哪些是必须守住的契约"。修改执行层前请先读完本文。

- 代码根目录：`backend/app/modules/quant/`
- 相关文档：[统一策略接口](./07-统一策略接口.md)、[模拟盘与实盘](./06-模拟盘与实盘.md)

---

## 1. 设计目标

| 目标 | 做法 |
| --- | --- |
| 策略只写一次 | 三种模式共用同一份 `Strategy` 与 `StrategyAPI`，策略不感知执行细节 |
| 决策规则只有一份 | 仓位换算、滑点、开仓门控、止损判定收敛到 `strategy/trading_base.py` 与 `execution/risk.py` |
| 记账只有一份 | 现金/持仓/成本/盈亏/保证金全部由 `execution/base.py::AccountLedger` 维护 |
| 时序可复刻 | "第 N 根收盘出信号、第 N+1 根开盘成交"在三种模式下用同一套口径实现 |
| 偏差可观测 | 成交价口径（`fill_basis`）、未成交量（`unfilled`）、被拒订单（`rejected`）全部落库 |

**非目标**：不追求三种模式逐笔完全相等。行情来源、流动性、手续费率天然不同，
本架构保证的是"决策逻辑一致 + 偏差可量化 + 偏差方向可解释"。

## 2. 分层结构

```text
                    ┌──────────────────────────────────────────┐
                    │  策略层  user_data/strategies/*.py        │
                    │  继承 Strategy，实现 on_bar 或 populate_*  │
                    └───────────────────┬──────────────────────┘
                                        │ api.buy() / sell() / sellshort() / buycover()
                    ┌───────────────────▼──────────────────────┐
                    │  接口层                                   │
                    │  回测: strategy/api.py::TradeAPI          │
                    │  实时: execution/api.py::StrategyAPI      │
                    │  —— 门控、定仓、下单请求构造都在这一层     │
                    └───────┬───────────────────────┬──────────┘
                            │ 回测：入队             │ 实时：submit 回调
                    ┌───────▼──────────┐   ┌────────▼─────────────┐
                    │ backtest/engine  │   │ execution/runner      │
                    │ 逐根 K 线驱动     │   │ run_tick 单次编排      │
                    └───────┬──────────┘   └────────┬─────────────┘
                            │                       │
                            │              ┌────────▼─────────────┐
                            │              │ 执行器 Executor       │
                            │              │ Paper: 本地虚拟撮合    │
                            │              │ Live: 币安下单+回查    │
                            │              └────────┬─────────────┘
                    ┌───────▼───────────────────────▼──────────┐
                    │  账本层 execution/base.py::AccountLedger  │
                    │  现金 / 持仓 / 成本 / 盈亏 / 保证金 / 风控  │
                    └───────────────────┬──────────────────────┘
                                        │
                    ┌───────────────────▼──────────────────────┐
                    │  行情层 execution/stream.py::MarketStream │
                    │  WS kline + bookTicker，REST 回补兜底      │
                    └──────────────────────────────────────────┘
```

| 模块 | 职责 | 不允许做的事 |
| --- | --- | --- |
| `strategy/trading_base.py` | 纯函数：周期换算、收盘判定、定仓、滑点、门控 | 不访问 DB / 网络 / 全局状态 |
| `execution/base.py::AccountLedger` | 撮合数学与账户状态 | 不决定"该不该下单" |
| `execution/api.py::StrategyAPI` | 策略可见接口，构造 `OrderRequest` | 不直接改账本 |
| `execution/runner.py::run_tick` | 一次 tick 的编排：行情→风控→策略→撮合→结果 | 不实现策略逻辑 |
| `execution/stream.py::MarketStream` | 行情缓存与收盘事件 | 不做交易决策 |
| `runtime/service.py::RuntimeManager` | 实例调度、行锁占位、持久化、对账 | 不碰撮合数学 |
| `backtest/engine.py` | 历史数据驱动同一套账本 | 不得自建第二套撮合公式 |

## 3. 关键数据结构

| 结构 | 位置 | 说明 |
| --- | --- | --- |
| `Candle` | `strategy/api.py` | `date/open/high/low/close/volume`，`date` 为 ISO 字符串 |
| `OrderRequest` | `execution/base.py` | `side/qty/signal_price/reason/symbol/client_order_id/qty_ratio` |
| `Fill` | `execution/base.py` | `side/qty/price/fee/pnl/reason/signal_price/timestamp` |
| `AccountLedger` | `execution/base.py` | 现金、多空持仓、成本、已实现盈亏、保证金、风控状态 |
| `TickResult` | `execution/runner.py` | 一次 tick 的价格/净值/持仓/成交/日志/口径/未成交量 |

`qty_ratio` 是一致性的关键字段：

- `> 0`：按比例开仓，**撮合时必须用成交价重算数量**；
- `= 0`：固定数量单，直接按 `qty` 撮合，仅受资金/持仓裁剪。

回测的 `execute_pending` 与实时的 `run_tick` 都按这条规则处理，因此"信号价"与"成交价"的
差额不会改变实际仓位比例。

## 4. 买入点判定链路

```text
① 行情窗口        已收盘 K 线（实时丢弃形成中那根；回测丢弃末尾未收盘根）
② 信号计算        策略只看到 <= 当前 bar 的数据，指标用截至当前的收盘价
③ 开仓门控        未熔断 + 无同向持仓/挂单（可扣减本 tick 待平仓量）+ ratio ∈ (0,1]
④ 定仓            预算 × ratio ÷（成交价 × (1 + 费率 + 滑点)）
⑤ 订单排队        回测：入队等下一根；实时：submit 回调入队，tick 末统一撮合
⑥ 成交与记账      下一根开盘价（近似时标注 mid_fallback）→ 滑点 → 手续费 → 深度裁剪
⑦ 输出            成交、未成交量、被拒订单、成交价口径全部随 TickResult 落库
```

### 4.1 行情窗口

- 实时：`MarketStream` 把 WS 推送的已收盘 K 线写入定长队列，形成中的那根单独存放；
  `run_tick` 用"已收盘窗口"作为信号窗口。
- REST 兜底：拉取窗口后由 `_resolve_signal_and_price` 判断末根是否收盘，未收盘则丢弃并按它的
  开盘价成交（等价于"下一根开盘"）。
- 回测：`run_backtest` 入口按 `bar_is_closed` 丢弃末尾一根未收盘 K 线（`dropped_unclosed`
  记录在结果里）。**这一步是防未来函数的关键**：数据文件通常是"下载到此刻"，末根往往正好
  是形成中的那根。

### 4.2 定仓公式

```text
预算 budget:
    leverage = 1（现货）     buy → cash            sellshort → equity
    leverage > 1（保证金）   buy/sellshort → free_margin × leverage

数量 qty = budget × ratio ÷ (price × (1 + fee_rate + slippage))
```

- `price` 是**成交价**，不是信号价。
- 按比例开仓时，接口层只算一个预估值用于门控；真正的数量在撮合那一刻用成交价重算，
  回测与实时走同一条公式。
- 显式传 `amount` 时 `qty_ratio = 0`，数量不再重算，但仍会被资金/持仓上限裁剪。

### 4.3 门控

```text
允许开仓 = (同向持仓 - 本 tick 待成交平仓量 <= 0) 且 (同向挂单量 <= 0)
          且 未触发回撤熔断
          或 策略显式声明 allow_position_add = True
```

扣减"待成交平仓量"是为了支持**同根反手**：策略先 `sell()` 再 `buy()` 时，账本持仓还没变，
若不扣减，随后的开仓会被误判为重复开仓而拒绝，反手只能等下一根。

### 4.4 成交与记账

| 环节 | 回测 | 模拟盘 | 实盘（真实下单） |
| --- | --- | --- | --- |
| 成交价 | 下一根 `open` | 新 bar `open`；拿不到则盘口中间价（标 `mid_fallback`） | 交易所真实成交均价 |
| 滑点 | 配置比例（买加卖减） | 配置比例（买加卖减） | 不叠加（真实价已含滑点） |
| 点差 | 由 `slippage` 近似 | `mid_fallback` 时按半价差修正到卖一/买一 | 真实盘口 |
| 手续费 | 配置费率 | 配置费率 | 交易所回填真实手续费，缺失时查成交流水 |
| 数量上限 | 资金/持仓 | 资金/持仓 + L1 深度 | 资金/持仓 + L1 深度 + 交易所过滤器 |
| 未成交 | 直接取消并记日志 | 记 `unfilled` 并留待下一 tick 补成交 | 记 `unfilled`（不补发市价单） |

## 5. 三种模式的时序

```text
回测
  bar N: open ── 执行上一根挂单 ── 风控(整根 low/high) ── 策略(收盘价) ── 记录净值
  bar N+1: open ── 成交本根信号（按 open 价）

模拟盘 / 实盘
  bar N 收盘事件 ── run_tick
        ① 风控（用 bar N 完整区间，按发现时市价成交）
        ② 补成交上一 tick 的深度余量（仅模拟盘）
        ③ 策略（窗口末尾 = bar N）
        ④ 按 bar N+1 的 open 撮合本轮订单
```

差异说明：

- **风控时点**：回测在 bar 内即可触发（用整根 `low/high`），实时只能在 bar 收盘后触发，
  因此止损最多滞后一根 K 线；周期大于 1 分钟时由 1 分钟心跳缩短到 1 分钟。
- **止损成交价**：回测按"止损价与开盘价中更差者"记账（等价交易所侧止损单）；模拟盘/实盘按
  "发现破位时的市价"成交，因为这两者只能在收盘后发市价单。两种口径都在结果里可追溯。
- **末根信号**：回测默认按末根收盘价撮合（兼容旧结果），`final_fill_basis="skip"` 时直接放弃，
  与实时"必须有下一根才能成交"一致。

## 6. 调度与并发

### 6.1 两层锁

| 层 | 作用范围 | 实现 |
| --- | --- | --- |
| 进程内 asyncio 锁 | 单进程内同一实例 | `_tick_lock(strategy_id)` |
| 数据库行锁 | 多副本 | `SELECT ... FOR UPDATE` + `last_tick_time` 占位 |

### 6.2 两类占位，互不干扰

| 占位 | 载体 | 窗口 | 用途 |
| --- | --- | --- | --- |
| 信号 tick | `last_tick_time`（数据库） | 半个实例周期 | 防止同一根 K 线被重复处理 |
| 风控心跳 | `_RISK_TICK_AT`（进程内存） | 30 秒 | 1 分钟止损检查的节流 |

**两者必须分开**：如果心跳也写 `last_tick_time`，1 分钟一次的频率会把信号周期的"半根窗"一直
刷新，结果是心跳自己被挡掉（止损延迟拉长到半个周期），或者真正的信号 tick 被判成"本根已处理"
而跳过（成交价整体晚一根）。

### 6.3 幂等

- `last_signal_bar`：同一根 K 线的信号只处理一次。
- `client_order_id` = `symbol + 信号bar + side + 序号`（≤36 字符），交易所侧可据此去重。
- 补成交订单**不复用** `client_order_id`，避免被交易所判为重复订单。

## 7. 运维与恢复

| 场景 | 行为 |
| --- | --- |
| 进程崩溃 / 重启 | 账本从 `quant_live_strategy.account` 快照恢复，含待补成交队列 |
| 实盘对账 | 每 30 秒（节流）用余额/成交/挂单覆盖现金、持仓、手续费、已实现盈亏 |
| 孤儿挂单 | 存活超过 60 秒自动撤销并告警 |
| 深度不足 | 记 `unfilled`；模拟盘下一 tick 补成交；同一笔最多重试一次，队列上限 5 笔 |
| 策略异常 | `status=2` + `last_error` 落库，页面可见；下次成功自动恢复 |
| 行情断线 | `wait_connected` 短暂等待后重连；超时退回 REST 轮询并对齐 bar 边界 |

## 9. 已知偏差（按可消除程度分层）

### 9.1 结构性偏差，无法用工程手段消除

| 偏差 | 原因 | 影响量级 |
| --- | --- | --- |
| 止损发现延迟 | 实时只能在 bar 收盘后判定 | 最多一根 K 线（1m 心跳可缩到 1 分钟） |
| 回测同根开平 | 回测可在开仓那根内触发止损 | 回测略优于实时，方向固定 |
| 深度只到 L1 | bookTicker 只有最优一档 | 大单被截断，偏差随单笔规模放大 |
| 现货不能做空 | 交易所限制 | 含空头分支的策略，实时结果不可比 |

### 9.2 已量化并可观测

| 偏差 | 观测方式 |
| --- | --- |
| 成交价来源 | `TickResult.fill_basis`：`next_open` / `mid_fallback` / `bar_close` / `stale` |
| 未成交量 | `TickResult.unfilled[]`（`reason=depth` / `depth_retry_failed`） |
| 被拒订单 | `TickResult.rejected[]` + 策略日志 |
| 口径假设 | 回测结果 `slippage_assumption` / `min_notional` / `final_fill_basis` |

### 9.3 参数层面

| 偏差 | 建议 |
| --- | --- |
| 回测 `slippage=0` | 结果偏乐观，启动时会告警；建议按点差 + 冲击成本设置 |
| 回测费率 ≠ 真实费率 | 实盘用交易所回填的真实手续费；回测按 VIP 等级设置 `fee_rate` |
| `min_notional=0` | 小资金回测会成交实盘必被拒的碎单；服务层应注入交易对真实下限 |

## 10. 扩展指南

### 10.1 新增一种执行模式

实现 `Executor` 协议的两个方法即可，策略与接口层无需改动：

```python
class MyExecutor:
    async def execute(self, order: OrderRequest, price: float, depth) -> Fill | None: ...
    def snapshot(self) -> dict: ...
```

接入点：`runtime/service.py::_build_executor`。

### 10.2 新增一个市场

市场差异集中在 `quant_market/`（表名、数据目录、柜台），执行层保持不变。
柜台适配只需提供"下单 / 查单 / 余额"三件事，撮合数学仍交给 `AccountLedger`。

### 10.3 修改撮合规则

只允许改 `AccountLedger.execute` 与 `trading_base` 中的纯函数，**禁止**在回测或执行器里再写一套
公式。改完必须同时跑：

```bash
cd backend
uv run pytest tests/test_quant_execution_parity.py tests/test_quant_parity.py tests/test_quant_engine.py -q
```
